# week. 2.3.2 — усиление безопасности

Это обновление не обещает «100% защиту» — такой гарантии не бывает. Оно закрывает найденные слабые места в текущей архитектуре week. и уменьшает последствия ошибок или злоупотребления одним аккаунтом.

## Что изменено

- Строже RLS и права таблиц: пользователь видит только свои/разрешённые данные.
- Участник общей задачи может менять только статус и чек-лист через проверяемые RPC, а не переписывать владельца, дату или название задачи.
- Публичный перебор профилей отключён. Поиск работает только по точному username, а имена подгружаются только для связанных пользователей.
- Администраторские проверки и RLS-хелперы вынесены в неэкспонируемую схему `private`.
- Браузер больше не создаёт профиль с произвольным email. Если профиль отсутствует, его восстанавливает серверная функция из `auth.users`.
- Добавлены лимиты на задачи, шаблоны, заявки, таймер, расписание и историю активности, чтобы один аккаунт не мог быстро заполнить базу.
- CSP блокирует inline JavaScript, `object`, чужие формы и лишние подключения.
- Supabase JS закреплён на конкретной версии.
- Service Worker кэширует только известные статические файлы и не открывает внешние URL из push-уведомлений.
- Edge Function требует обязательный `CRON_SECRET` и принимает push-endpoint только от известных push-сервисов.
- Пароль при регистрации на клиенте: минимум 10, максимум 128 символов.
- Технические ошибки загрузки больше не показывают пользователю имена таблиц/политик.

## Порядок установки

### 1. Сделай резервную копию

Перед SQL-миграцией сохрани текущую базу. Не публикуй дамп в GitHub.

### 2. Выполни SQL

В Supabase → SQL Editor запусти файл:

`MIGRATION_2_3_2_SECURITY.sql`

Он рассчитан на базу, где уже установлены миграции 2.1, 2.2 и 2.3. Старые пользовательские данные он не удаляет.

После успешного запуска можешь выполнить `SECURITY_CHECK_2_3_2.sql`. Первый, второй и третий проверки должны вернуть 0 строк, а последняя — `true` во всех колонках.

### 3. Замени файлы сайта

В GitHub замени:

- `index.html`
- `app.js`
- `sw.js`

И добавь новый файл:

- `bootstrap.js`

`style.css` и `config.js` менять не нужно.

После публикации один раз полностью перезагрузи сайт. На установленной PWA при необходимости закрой приложение и открой заново, чтобы новый Service Worker вступил в работу.

### 4. Обнови Edge Function

Замени:

`supabase/functions/send-task-reminders/index.ts`

и снова разверни `send-task-reminders`.

В Secrets функции должен быть `CRON_SECRET` длиной не меньше 32 случайных символов. Планировщик, который вызывает функцию, обязан отправлять тот же секрет в заголовке:

`x-cron-secret: ...`

Не помещай `CRON_SECRET`, секретный ключ Supabase или приватный VAPID-ключ в GitHub или `config.js`.

Для браузера допустим только publishable key вида `sb_publishable_...`. Секретный ключ (`sb_secret_...`) должен оставаться только на сервере/в Edge Function.

## Настройки Supabase, которые надо проверить вручную

В Authentication:

1. **Confirm Email** — включено.
2. **Anonymous sign-ins** — выключено, если ты их специально не используешь.
3. Минимальная длина пароля на сервере — не меньше 10 символов. Можно поставить 12.
4. **Site URL** — только рабочий HTTPS-адрес week.
5. В Redirect URLs оставь только реально нужные адреса. Для рабочего сайта не используй широкий `**`, если он не нужен.
6. Посмотри Authentication → Rate Limits. Для школы не занижай лимиты слишком сильно: много учеников могут выходить в интернет через один IP.
7. Открой Supabase Security Advisor и проверь, что после миграции нет новых замечаний по RLS/привилегиям.

## CAPTCHA и MFA

Supabase поддерживает CAPTCHA/Turnstile и MFA, но текущий интерфейс week. пока не передаёт CAPTCHA token и не содержит MFA-flow. Поэтому **не включай CAPTCHA в Dashboard на этой версии**, иначе вход/регистрация могут перестать работать. Для публичной регистрации это хороший следующий отдельный шаг.

Для администраторского аккаунта используй отдельный длинный уникальный пароль и не повторяй его на других сайтах. MFA можно добавить отдельным обновлением.

## Ограничение GitHub Pages

В `index.html` уже есть строгий CSP и защита от встраивания через JavaScript. Но такие заголовки, как полноценный `frame-ancestors`, HSTS и `X-Content-Type-Options`, надёжнее задавать на уровне HTTP-сервера/CDN. Если week. станет школьным сервисом для большого числа людей, лучше использовать хостинг или прокси, где можно задавать security headers.

## Если что-то сломалось после SQL

Не запускай старый `supabase.sql` поверх базы. Сначала сохрани текст ошибки из SQL Editor. Если миграция завершилась транзакцией с ошибкой, изменения из неё не применятся.
